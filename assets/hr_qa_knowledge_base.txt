SECTION 4 — PROJECT 1: BANK TRANSACTION SYSTEM
===============================================================================

PROJECT OVERVIEW The Bank Transaction System is a backend development
project built with Node.js, Express 5, MongoDB, and Mongoose. It
includes JWT-based authentication, password hashing with bcryptjs,
transaction handling, an immutable double-entry ledger, idempotency
keys, and Google OAuth 2.0 for email notifications. The ledger is
treated as the source of truth for account balances. MongoDB sessions
and transactions are used to maintain consistency during money
transfers.

Q22. Tell me about your Bank Transaction System. I built a Bank
Transaction System focused on the correctness and reliability of
financial operations. The backend uses Node.js and Express, with MongoDB
and Mongoose for data storage. A key design decision is using an
immutable double-entry ledger as the source of truth for balances.
Transfers use MongoDB transactions so related database operations
succeed or fail together. I also worked with idempotency keys to prevent
duplicate processing when a request is retried.

Q23. Why did you choose this project? I wanted to work on a problem
where backend correctness matters. A banking system is not only about
creating APIs; it requires careful handling of balances, concurrent
requests, duplicate requests, and failures. It gave me an opportunity to
understand transaction management and data consistency in a practical
way.

Q24. What is the technology stack? The backend uses Node.js and Express
5. MongoDB is the database, with Mongoose for object data modeling. JWT
is used for authentication, bcryptjs for password hashing, and Google
OAuth 2.0 is used for email notification integration.

Q25. Explain the ledger-based approach. Instead of treating a mutable
balance field as the only source of truth, the system records financial
movements in an immutable double-entry ledger. Each transfer is
represented by corresponding debit and credit entries. The account
balance can be derived from the ledger entries, which provides an
auditable record of how the balance changed.

Q26. Why is the ledger the source of truth? A single mutable balance
value tells us the current number but does not, by itself, explain the
history behind it. Ledger entries preserve the transaction history. This
makes financial movements traceable and supports reconciliation and
auditing. A cached or derived balance can be used for performance, but
the ledger remains the authoritative record.

Q27. What is double-entry bookkeeping? Double-entry bookkeeping records
each financial transaction in at least two corresponding entries: one
side is debited and the other side is credited. For a transfer between
two accounts, the amount removed from one account is reflected as an
amount added to the other. The entries must balance, which helps
maintain accounting consistency.

Q28. How do you handle a money transfer? At a high level, the backend
validates the request and the participating accounts, then performs the
related ledger writes within a MongoDB transaction. The debit and credit
entries must be committed together. If an operation fails, the
transaction is rolled back so the system does not leave only one side of
the transfer recorded.

Q29. Why use MongoDB transactions? A transfer involves multiple related
writes. MongoDB transactions allow those operations to be treated
atomically: either all required writes commit, or none of them do. This
helps prevent inconsistent states such as recording a debit without its
corresponding credit.

Q30. What is a MongoDB session? A session groups database operations
under a common transactional context. In this project, the session is
used with MongoDB transactions so the operations that make up a transfer
are executed within the same transaction boundary.

Q31. What is concurrency, and why does it matter in banking? Concurrency
occurs when multiple requests are processed at overlapping times. For
example, two transfer requests may try to use the same account balance.
If the system does not handle concurrent operations correctly, it can
produce inconsistent results. Transaction boundaries and appropriate
consistency checks help protect the data.

Q32. How do you prevent duplicate transfers? I use idempotency keys. A
client can send a unique key with a transfer request. If the same
request is retried with the same key, the backend can recognize that it
has already been processed rather than creating another transfer. This
is important when a client times out and cannot tell whether the
original request succeeded.

Q33. What is idempotency? An operation is idempotent when repeating the
same request does not create additional unintended effects. For a
payment or transfer API, idempotency helps ensure that retrying a
request does not accidentally execute the financial operation twice.

Q34. What happens if the client retries after a timeout? The backend
checks the idempotency key associated with the request. If the request
has already been completed, the system should return the existing result
instead of processing a second transfer. This protects against duplicate
effects caused by network uncertainty.

Q35. How do you handle authentication? The system uses JWT-based
authentication. After successful authentication, a token is used to
identify and authorize subsequent protected API requests. Passwords are
hashed using bcryptjs rather than stored as plain text.

Q36. Why hash passwords with bcryptjs? Passwords should never be stored
in plain text. bcryptjs applies a one-way password hashing process with
a configurable work factor, making it more difficult for an attacker to
recover passwords if the password database is exposed.

Q37. Is Google OAuth 2.0 used for login? No. In this project, Google
OAuth 2.0 is used for email notification functionality. It should not be
described as the system’s login or authentication mechanism. JWT is used
for application authentication.

Q38. How are email notifications handled? The project uses Google OAuth
2.0 to authorize the email integration for sending notifications. This
is separate from the JWT-based authentication used by the application.

Q39. What was the most important design decision? Treating the immutable
double-entry ledger as the source of truth was an important decision. It
gives the system a traceable financial history. MongoDB transactions and
idempotency keys complement that design by helping preserve consistency
and prevent duplicate processing.

Q40. What was challenging about this project? The main challenge was
thinking beyond the normal CRUD approach. Financial operations need to
account for failures, retries, and concurrent requests. Designing around
ledger entries, transaction boundaries, and idempotency helped me
understand why correctness is essential in backend systems.

Q41. What would you improve next? I would strengthen automated testing
for concurrent transfers, retries, transaction failures, and boundary
conditions. I would also improve observability with structured logs and
performance metrics, and review indexing and query patterns as the data
volume grows.

Q42. How would you test a transfer system? I would test successful
transfers, insufficient funds, invalid accounts, repeated requests with
the same idempotency key, concurrent transfers, and failures during a
transaction. I would verify that debit and credit ledger entries remain
balanced and that failed transfers do not leave partial writes.

Q43. What did you learn from this project? I learned that backend
development is not just about building endpoints. Data integrity,
atomicity, authentication, retry behavior, and auditability are equally
important. I also learned to think about failure scenarios before
assuming that the happy path is enough.

Q44. Explain the project in one minute. I built a backend Bank
Transaction System using Node.js, Express 5, MongoDB, and Mongoose. It
uses JWT for authentication and bcryptjs for password hashing. The main
design is an immutable double-entry ledger that acts as the source of
truth for balances. MongoDB transactions keep related transfer
operations atomic, while idempotency keys protect against duplicate
transfers when requests are retried. Google OAuth 2.0 is used only for
email notifications. The project helped me understand reliable backend
and financial data design.

SECTION 5 — PROJECT 2: DIGITAL TWIN — AGENTIC RAG PERSONAL ASSISTANT
===============================================================================

PROJECT OVERVIEW The Digital Twin is a personal AI assistant designed to
answer questions using personal knowledge sources and to use web search
for general or current information when appropriate. The project uses
Python, LangChain, OpenAI models, ChromaDB, embeddings, a multi-format
ingestion pipeline, an agent/tool-calling workflow based on ReAct, and a
Streamlit interface. The knowledge pipeline supports PDFs, code files,
CSVs, and text-based documents. The system uses prompt instructions and
local-context prioritization to reduce unsupported answers. Conversation
history is handled separately from the vector knowledge store.

Q45. Tell me about your Digital Twin project. I built a Digital Twin
personal assistant that can answer questions using my own knowledge
sources and use web search when a question needs general or current
information. I used LangChain to organize the retrieval and agent
workflow, ChromaDB for vector search, and Streamlit for the interface.
The agent can choose an appropriate tool, such as local retrieval or web
search, instead of relying on a single fixed response path.

Q46. Why did you build a Digital Twin? I wanted to explore how an AI
assistant could represent a person’s knowledge and respond using
relevant personal context. It also gave me a practical way to learn RAG,
vector databases, prompt engineering, tool calling, conversational
memory, and agentic workflows.

Q47. What is RAG? Retrieval-Augmented Generation combines information
retrieval with language generation. The system first retrieves relevant
information from a knowledge source and then provides that context to
the language model to help generate a grounded answer. This is useful
when the answer should be based on specific documents rather than only
the model’s general training knowledge.

Q48. What is Agentic RAG? Agentic RAG adds an agent that can decide how
to approach a question. Instead of always performing the same retrieval
step, the agent can select a suitable tool, such as a vector retriever
or web search, observe the result, and use it to form an answer.

Q49. What is the difference between traditional RAG and Agentic RAG? In
a basic RAG pipeline, a query typically follows a predefined
retrieval-and-generation sequence. In Agentic RAG, an agent can select
tools or actions based on the question and available information. This
makes the workflow more flexible, although it also requires careful tool
design and evaluation.

Q50. Explain the ReAct framework. ReAct stands for Reasoning and Acting.
It is a framework in which an agent alternates between deciding what
action is needed and using a tool to obtain information. The tool’s
output is then used in the next step before the agent produces its final
response. In my project, this allows the agent to choose between local
knowledge retrieval and web search when appropriate.

Q51. Explain the ReAct flow in your project. A user submits a question.
The agent evaluates which information source is appropriate. If the
question is about my profile or projects, it can use the local RAG
retrieval tool. If the question requires general or current information,
it can use web search. The agent receives the tool result and then
generates the response using the available evidence.

Q52. What tools does your agent use? The main tools are local vector
retrieval from the ChromaDB knowledge base and web search through a
search tool. The agent selects between these based on the nature of the
question.

Q53. Why not use web search for every question? Personal questions
should be answered from the personal knowledge base, not from unrelated
web pages. Local retrieval provides information specific to my profile
and projects. Web search is more appropriate for general or current
questions. Choosing the source based on intent helps keep answers
relevant.

Q54. Why use ChromaDB? ChromaDB is a vector database that stores
embeddings and supports similarity-based retrieval. It allows the
application to retrieve semantically related content even when the
wording of the question differs from the wording in the source
documents.

Q55. What are embeddings? Embeddings are numerical representations of
text that capture semantic information. Texts with related meanings can
have vectors that are close in the embedding space. A vector database
uses these representations to retrieve relevant chunks for a query.

Q56. What is chunking, and why is it needed? Chunking splits large
documents into smaller pieces before embedding. This makes retrieval
more focused because the system can retrieve a relevant section rather
than passing an entire large document to the model. Chunk size and
overlap affect context quality and retrieval behavior.

Q57. Which document types does your ingestion pipeline support? The
pipeline supports PDFs, code files, CSV files, and text-based documents.
It uses appropriate loaders for supported formats, then splits and
embeds the extracted content for retrieval. Do not claim that every
image, audio, or video format is fully supported unless that capability
has actually been implemented and tested.

Q58. How does the knowledge ingestion process work? The application
reads supported files from the assets or knowledge directory, extracts
their content using format-appropriate loaders, splits the content into
chunks, creates embeddings, and stores those vectors in ChromaDB. At
query time, relevant chunks can be retrieved and passed to the language
model.

Q59. How do you reduce hallucinations? I use prompt instructions that
prioritize retrieved local context for personal questions. The retrieval
tool provides relevant source material, and the prompt tells the model
not to invent details when the information is missing. The agent also
chooses between local retrieval and web search based on the question.
These measures reduce the risk of hallucination, but they do not
guarantee that the model will never make a mistake.

Q60. What happens if the answer is not in the knowledge base? The system
should avoid inventing a personal fact. It can indicate that the
information is not available in the provided context. If the question is
general and needs external information, the agent may use web search
when appropriate.

Q61. How do you distinguish personal questions from general questions?
The agent uses the intent and content of the question to select a tool.
Questions about my background, skills, or projects should use the
personal knowledge base. Questions about general or current topics may
use web search. The purpose is to select the source that best matches
the question.

Q62. What is conversational memory? Conversational memory stores
information from previous turns so an assistant can maintain context
during a conversation. In this project, conversation history is handled
separately from the ChromaDB vector knowledge base. They solve different
problems: one preserves conversation context, while the other retrieves
information from documents.

Q63. Is chat history the same as the vector database? No. Chat history
stores conversation messages and supports continuity across turns. The
vector database stores embedded document chunks and supports semantic
knowledge retrieval. Updating one does not automatically update the
other.

Q64. If you update a knowledge file, does ChromaDB update automatically?
Not necessarily. The application must run its ingestion or re-indexing
process so the updated file is loaded, chunked, embedded, and written to
the vector store. If the agent or vector store is cached in the running
Streamlit process, the cache may also need to be cleared or the app
restarted so the new index is loaded.

Q65. What is the role of Streamlit? Streamlit provides the interactive
web interface. Users can submit questions and view the assistant’s
responses without needing to interact directly with the Python backend
or command line.

Q66. Why did you use LangChain? LangChain provides components for
connecting language models, prompts, retrievers, tools, and agent
workflows. It helped me organize the RAG pipeline and tool-calling
behavior without having to implement every integration from scratch.

Q67. What was the most challenging part of the Digital Twin? One
challenge was making the system work reliably across the full pipeline:
loading different file formats, creating embeddings, retrieving useful
context, selecting tools, and deploying the application. I learned that
a working model call is only one part of an AI application; data
ingestion, dependencies, storage, and runtime behavior matter just as
much.

Q68. What deployment issues did you encounter? I encountered environment
and storage-related issues while deploying, including ChromaDB SQLite
database access problems and dependency compatibility/build issues. I
worked through the deployment constraints and used an
ephemeral/in-memory ChromaDB approach for the cloud demo where
persistent local storage was not reliable. This means the vector index
is recreated from the knowledge files when the app starts, rather than
relying on a durable local database file.

Q69. Is your ChromaDB data persistent in the cloud? For the cloud demo
configuration using an ephemeral/in-memory store, the vector index is
not durable across a fresh runtime. It is rebuilt from the available
knowledge files when the application initializes. This is different from
persistent database storage.

Q70. What would you improve in the Digital Twin? I would improve
retrieval evaluation, add more systematic testing for tool selection,
measure latency and retrieval quality, and make the ingestion process
more robust when files change. For a production deployment, I would also
use durable external storage and stronger monitoring rather than relying
on ephemeral local storage.

Q71. How do you evaluate whether retrieval is good? I would prepare
representative questions with expected source passages, then check
whether the retriever returns the right content. I would evaluate
relevance, completeness, and whether the final answer is supported by
the retrieved material. I would also test questions that are
intentionally outside the knowledge base.

Q72. What is the limitation of your Digital Twin? Its answer quality
depends on the quality and freshness of the knowledge sources,
retrieval, and model behavior. If relevant information is missing or
poorly indexed, the answer may be incomplete. Tool selection and
generation can also make mistakes, so the system needs testing and
monitoring.

Q73. Explain the project in one minute. My Digital Twin is an Agentic
RAG personal assistant built with Python, LangChain, ChromaDB, OpenAI,
and Streamlit. It ingests supported files such as PDFs, CSVs, code, and
text documents, converts their content into embeddings, and retrieves
relevant information from ChromaDB. The agent follows a ReAct-style tool
workflow and can choose between local retrieval for personal questions
and web search for general or current questions. I use prompt
instructions to prioritize local context and avoid unsupported personal
claims. The project helped me understand how retrieval, tool selection,
memory, and deployment fit together in an AI application.
